One Timer, Many Views

Put the timer machine on a screen without the screen ever disagreeing with it.

Last time you built TimerCore: a cook time that cannot be malformed and a timer that cannot be in an impossible state. It runs on your Mac and it has no screen. Today it gets one, on the phone in your pocket.

By the end of the lab you will have a keypad on your iPhone whose Start button turns green only when the time is real. The interesting part is not the buttons. It is a single rule that makes a whole family of interface bugs impossible, and we will spend the lecture earning it.

Where Lesson 1 left us

Before I add anything, a quick warm-up. In your own words: what does TimerMachine.send do with an event that is not legal in the current state? Say it, or type it in the chat, then go on.

Right: it refuses the event, leaves the state alone, and writes an ignored line to the log. Hold on to that, because it comes back in the lab. Today's box sits on top of TimerCore and adds no rules of its own. Its whole job is to show what the machine says.

The easy way to build a screen

Here is how most of us would build the keypad the first time. Keep what was typed in a string. Keep a flag, isValid, next to it, and set it to true when the fourth digit arrives. The Start button turns green when the flag is true. Four keys in, everything is right.

A week later someone adds a backspace key. It removes the last character from typed, so the display now shows three digits.

But the backspace code never touched isValid. The flag still says true, the button is still green, and a three-digit time starts counting down. No line of code is wrong on its own. The bug lives in the gap between two facts that were supposed to agree.

Say we patch the backspace to reset isValid. Name one more way the flag can still go stale.

Any other writer of typed: paste, clear, a long press for 00. Each must remember. The fix: store no flag.

Pause here and answer before you go on. A guess is fine; the point is to commit to one.

Every new writer of typed inherits the duty to update the flag, forever. You can be careful, or you can arrange things so there is nothing to be careful about. The rest of the lecture is the second option.

Store the cause, compute the effect

So we store only causes. There are exactly two: what the user typed, and what has happened to the timer. Both are values you already have from Lesson 1: a String and a TimerMachine.

Everything else is an effect, and effects are computed every time someone reads them. parsed runs your Lesson 1 parser on typed. time is the success value or nothing. hint turns the result into the line under the display. There is no isValid to forget, because validity is a question asked of typed at the moment it is needed.

The screens only read. The keypad reads the computed properties; the view that picks a screen and the running screen read the machine. No view keeps a copy of anything.

That is the rule for the whole course, not just today: store what happened, compute what it means, and let views read only the meaning.

Seen this in Go?

Go

  • one struct, shared by pointer
  • you tell readers it changed

Swift

  • one @Observable class
  • readers found by reading

The break: nobody subscribes by hand.

In Go, when several goroutines need the same state, you share one struct by pointer and guard it, and when it changes you tell whoever cares, usually over a channel you wired up yourself.

Here the sharing half is the same: one Countdown object, handed to every view. That is why it is a class and not a struct like TimerMachine.

The telling half is where the analogy breaks. There is no channel and no subscribe call. A view becomes a reader by reading, and the next slides show how SwiftUI notices.

How SwiftUI knows what to redraw

You never tell SwiftUI to redraw. So how does the hint change when you press a key? One line on the class, @Observable, does it.

SwiftUI runs a view's body to draw it. Suppose the keypad's body reads countdown.typed, directly or through hint.

Observation records that read against that view. This is the subscription: reading is what signs you up.

Later a tap calls press, which assigns to typed. The setter the macro generated announces the change. This is the only step your code performs, and it is an ordinary assignment.

Every view whose record contains typed is marked to run again on the next frame, and only those. Apple puts it in one sentence: a view updates when an observable property changes and its body reads that property (Migrating to the Observable macro).

You tap 4. Which bodies run again: ContentView, KeypadView, or both?

Only KeypadView. It read typed. ContentView read only machine, and typing never writes machine.

Use the loop you just saw. Commit to an answer, then advance.

If you said both, you were treating countdown as the thing that changed. Observation is finer than that: it tracks each stored property separately. In the lab you will prove this with a test instead of taking my word for it.

Here is the picture as code. You will type all of it in the lab, so for now find the three parts. Bodies marked with an ellipsis are filled in there.

The causes: two stored properties. private(set) means any view can read them but only this class can write them.

The effects: computed properties. Notice there is no stored copy of anything here; each one is recalculated from typed when read.

The only writers. Two edit typed; three send an event to the timer machine, so Lesson 1's table still decides every transition.
