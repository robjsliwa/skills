One Phone, Many Views

Put the call machine on a screen without the screen ever disagreeing with it.

Last time you built PhoneCore: a phone number that cannot be malformed and a call that cannot be in an impossible state. It runs on your Mac and it has no screen. Today it gets one, on the phone in your pocket.

By the end of the lab you will have a dial pad on your iPhone whose Call button turns green only when the number is real. The interesting part is not the buttons. It is a single rule that makes a whole family of interface bugs impossible, and we will spend the lecture earning it.

Where Lesson 1 left us

Before I add anything, a quick warm-up. In your own words: what does CallMachine.send do with an event that is not legal in the current state? Say it, or type it in the chat, then go on.

Right: it refuses the event, leaves the state alone, and writes an ignored line to the log. Hold on to that, because it comes back in the lab. Today's box sits on top of PhoneCore and adds no rules of its own. Its whole job is to show what the machine says.

The easy way to build a screen

Here is how most of us would build the dial pad the first time. Keep what was typed in a string. Keep a flag, isValid, next to it, and set it to true when the tenth digit arrives. The Call button turns green when the flag is true. Ten keys in, everything is right.

A week later someone adds a backspace key. It removes the last character from typed, so the display now shows nine digits.

But the backspace code never touched isValid. The flag still says true, the button is still green, and a nine-digit number goes out to Twilio. No line of code is wrong on its own. The bug lives in the gap between two facts that were supposed to agree.

Say we patch the backspace to reset isValid. Name one more way the flag can still go stale.

Any other writer of typed: paste, clear, a long press for +. Each must remember. The fix: store no flag.

Pause here and answer before you go on. A guess is fine; the point is to commit to one.

Every new writer of typed inherits the duty to update the flag, forever. You can be careful, or you can arrange things so there is nothing to be careful about. The rest of the lecture is the second option.

Store the cause, compute the effect

So we store only causes. There are exactly two: what the user typed, and what has happened to the call. Both are values you already have from Lesson 1: a String and a CallMachine.

Everything else is an effect, and effects are computed every time someone reads them. parsed runs your Lesson 1 parser on typed. number is the success value or nothing. hint turns the result into the line under the display. There is no isValid to forget, because validity is a question asked of typed at the moment it is needed.

The screens only read. The dial pad reads the computed properties; the view that picks a screen and the call screen read the call. No view keeps a copy of anything.

That is the rule for the whole course, not just today: store what happened, compute what it means, and let views read only the meaning.

How SwiftUI knows what to redraw

You never tell SwiftUI to redraw. So how does the hint change when you press a key? One line on the class, @Observable, does it.

SwiftUI runs a view's body to draw it. Suppose the dial pad's body reads phone.typed, directly or through hint.

Observation records that read against that view. This is the subscription: reading is what signs you up.

Later a tap calls press, which assigns to typed. The setter the macro generated announces the change. This is the only step your code performs, and it is an ordinary assignment.

Every view whose record contains typed is marked to run again on the next frame, and only those. Apple puts it in one sentence: a view updates when an observable property changes and its body reads that property (Migrating to the Observable macro).

You tap 4. Which bodies run again: ContentView, DialerView, or both?

Only DialerView. It read typed. ContentView read only call, and typing never writes call.

Use the loop you just saw. Commit to an answer, then advance.

If you said both, you were treating phone as the thing that changed. Observation is finer than that: it tracks each stored property separately. In the lab you will prove this with a test instead of taking my word for it.

Here is the picture as code. You will type all of it in the lab, so for now just find the three parts. Bodies marked with an ellipsis are filled in there.

The causes: two stored properties. private(set) means any view can read them but only this class can write them.

The effects: computed properties. Notice there is no stored copy of anything here; each one is recalculated from typed when read.

The only writers. Two edit typed; three send an event to the call machine, so Lesson 1's table still decides every transition.
